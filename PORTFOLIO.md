# Drift — Portfolio

**Current version:** v2.1.0

## What it is

A gravity-surfing endless runner built as a single-file web game (PixiJS/WebGL with a Canvas 2D fallback), shipped as an Android app via Capacitor, with an AWS serverless leaderboard backend and fully automated infrastructure deployment.

## Highlights

- **Sirius death-narrator + full additive visual overhaul (v2.0.0 → v2.1.0)** — the headline of the v2.0.0 release is **Sirius**, a complete death-narrator arc: a fully-powered Ascension run on first death, a one-time second-death fake-out, then Sirius's reveal + a guaranteed revive — followed by ongoing difficulty-scaled revive chances on later deaths (Normal 10% / Hard 7% / Extreme + Impossible 5%), most a one-line revive and ~30% a multiple-choice cosmic quiz where a right *or* charmingly-wrong answer revives you, plus survival-tiered death-screen roasts when none procs. Shipped alongside a ground-up visual overhaul that rebuilt every effect family on one additive rendering recipe (constant-thickness vector strokes + baked soft-sprite blooms — no `shadowBlur`, per-frame gradients, or full-screen fills), player-facing **Render Quality** (DPR cap) and **frame-rate-cap** settings, and a long-session heat-reduction pass. **v2.1.0** adds **Helios** — an 8th orb unlocked through the Sirius progression — plus a controls / spawn-spacing / difficulty tuning pass
- **Orb skill-tree rework — single-rank / active-budget model (v1.9.0)** — the original multi-rank "grind every node" trees were migrated, one orb at a time, to a single-rank + active-point-budget model: each node is unlocked once with crystals, then toggled active/inactive within a limited active-point budget, so a run's identity comes from build choice rather than total grind. The engine was generalized into a reusable orb-keyed module (`ActiveBudget`) — adding a reworked orb is now a config registration plus a `TREE_DEFS` entry rather than a copy-paste of the budget/UI system. Roamer and Phantasm were built in this model; **all five original orbs (Drifter, Phantom, Inferno, Warp, Bulwark)** have now been migrated, each adding bespoke mechanics and entities — e.g. Phantom's decoy clones, homing blade, and a one-shot cheat-death; Inferno's orbiting fireball capstone, spreading burn-zone firefield, and per-cast wave-count engine; Warp's Singularity (the next hyperspeed snaps to max stacks and tears a planet-devouring rift on exit); and Bulwark's Dead Star (every 30 shield-stacks lost implodes the field into a 10-hit golden shield whose EMP bursts chain indefinitely). Each migration ships a schema-versioned, one-time save migration that refunds legacy investments at the old rates, plus a shape-based cloud-merge guard so a stale PGS snapshot can't resurrect old nodes for free. The first-death "rainbow orb" run was replaced by **Ascension** — a one-shot, fully-powered Phantasm run triggered by a cutscene on first death.
- **Battery, tutorial, and balance pass (v1.6.4)** — three things shipped in one release. (1) Battery: a STATIC skill-tree menu was burning ~10 % battery in 10–15 minutes on test devices because the Pixi stage was rendering at full FPS behind a fullscreen overlay, six overlays were compositing `backdrop-filter: blur` every frame, the orb-preview loop was running while hidden, and there was no FPS cap. Fixed by gating the Pixi render loop when an overlay covers the canvas, removing the unnecessary backdrop blurs, gating the preview loop on visibility, capping FPS (30 in static menus, 60/120/uncapped during gameplay per a new user-facing setting), and wiring `visibilitychange` + Capacitor `App` lifecycle handlers to halt rendering and duck music when backgrounded. (2) Tutorial: a 13-step first-launch guided sequence now teaches attract / repel, the four base powerups, pair combos, the burst gesture, the streak meter, and the wall-death warning, with a persistent `drift_tutorial_completed` flag in `localStorage` synced into the PGS snapshot so each pilot sees it exactly once across devices. (3) Balance: burst cooldown unified to 30 s for every orb (was 20 s default) with three trees gaining per-kill / per-cast burst-CD reductions to interact with it (Drifter's Restless Orb at −10/−20/−30 %, Inferno's Coronal Hold at −0.25/−0.50/−1 % per nova kill, Warp's renamed Momentum at −0.1/−0.2/−0.3 % per hyperspeed kill — the latter a complete rework from the old destroy-radius mechanic). Speed cap reached at 2:00 (was 3:00) and a second pricing pass took another −50/−45/−40/−35/−30 % off node costs across the orbs. Critical fixes alongside: SHOP button hidden behind Android gesture nav on S23 Ultra-class devices fixed via `viewport-fit=cover` + `env(safe-area-inset-*)` CSS + `WindowCompat.setDecorFitsSystemWindows(getWindow(), false)` Android edge-to-edge wiring; Ghostlight visual was a no-op (function existed but didn't render) — now properly clones the EMP burst structure with purple coloring; tree UI got a new FROZEN node state for the case where a prereq was refunded but the dependent node still has ranks (was misleadingly showing LOCKED)
- **Per-orb skill trees + tree progression system (v1.6.3)** — five non-exclusive trees, ~30 nodes plus 11 capstones (Drifter has 3 — its identity capstone slot). Each tree has three paths (T1/T2/T3) with a shared cost table multiplied by per-orb scale, then a separate, less-aggressive scale for capstones — so node grind is cheap (Drifter T1 R1 = 2 500 💎) but capstones stay aspirational (Drifter capstone = 19 500 💎). Tree state persists in `localStorage`, syncs to the PGS cloud-save snapshot, and respec works at single-node (4k flat) or full-tree (1.4k × invested ranks) granularity. The whole system is data-driven from a single `TREE_DEFS` object: every UI screen, tooltip, prereq check, cost, and apply-effect path reads from the same source of truth, so adding a node is a single-table edit. Mechanic reworks across the trees include a single-shared-timer hyperspeed rewrite (replaces the per-pickup independent timers that had caused stack-stacking edge cases since v1.0), a destroy-to-powerup proc family with cross-tree guard rails (Siphon / Soulbound / Firebrand / Slipstream / Bastion II share a kill-site cue language but each has its own internal cooldown to break feedback loops), and capstone HUD countdown rings driven by a single reusable conic-gradient component
- **IMPOSSIBLE difficulty + post-cap progression (v1.6.3)** — a fourth difficulty unlocked by beating EXTREME's 10-minute apocalypse. Speed cap is reached at 1:00 instead of 3:00, then the body cap and scroll speed continue ramping (+10 %/min speed, +1 max body every 2 min) for an unbounded endurance test. The serverless leaderboard backend gained a stricter Lambda allowlist for the new difficulty, and per-difficulty leaderboard tabs were extended to surface it. Crystal payout is 1.5× to compensate the difficulty curve
- **Google Play Games cloud save — custom Capacitor Kotlin plugin (v1.6.2)** — built a Capacitor 8 plugin from scratch (`PgsSavedGamesPlugin.kt`) bridging Google's `play-services-games-v2` Snapshots API to the web-based game, because no official or current community plugin exists for PGS v2 in the Capacitor ecosystem. The plugin exposes `signIn`, `isAuthenticated`, `readSnapshot`, and `writeSnapshot` methods, each wrapping Google's `Task<T>` into `PluginCall` resolve/reject, with `PlayGamesSdk.initialize()` wired into `MainActivity.onCreate` and APP_ID meta-data in the manifest. On the JS side, a small module handles OAuth sign-in, opens the snapshot with `RESOLUTION_POLICY_MOST_RECENTLY_MODIFIED`, and applies a **max-per-field merge** (crystals = max of local/remote, unlocked orbs = set union, scores = combined then top-5 per difficulty, activeOrb stays local). Writes are 2 s debounced so rapid save mutations don't spam the Snapshots API. Opt-in only: first-launch prompt + settings toggle, and all local save paths are untouched when the user is signed out. Non-Android platforms no-op cleanly via `Capacitor.getPlatform()` gating. This is the first Google-cloud-backed persistence in the project — the existing AWS leaderboard is one-way write-only — and closes the "uninstall = permanent progress loss" gap that was the biggest open risk before production release
- **Frame-rate decoupled physics (v1.6.1)** — the entire physics model was migrated from implicit 60 Hz frame-step to a dt-scaled variable timestep against a 120 fps baseline. 29 Category A sites were multiplied by `dtScale`, frame-count spawn cadences were converted to wall-clock ms timestamps, and a `decay()` helper standardised exponential drag patterns. This fixed the "game plays easier on 60 fps devices" bug that had been hiding in the codebase since v1.0, and paired with the earlier real-time-timer refactor means gameplay now feels identical at 30/60/120 Hz and under Android low-power throttling
- **Difficulty rebalance with spawn-distance enforcement (v1.6.2)** — post-cap speed ramp softened from +0.25/min to +0.10/min (unbounded growth nerfed), max body count ramp delayed from 2:00 to 3:00 with increments every 90 s (was 60 s), and a minimum 80 px AABB spawn distance added to prevent unfair clump spawns. Tuning driven by the analytics-dashboard death-cause breakdown
- **DPR-scaled sprite/atlas pipeline (v1.6.2)** — introduced an `atlasScale()` helper (capped at 2×) and applied it across 13 offscreen canvases: `starAtlases`, `ringsCanvas`, `glowCanvas`, `getBgVignetteCanvas`, `getShieldRingCanvas`, `buildEyeVeinSprite`, `buildSkullFaceSprite`, `buildMirrorBodySprite`, `buildScreamingStaticSprite`, `buildHeartStaticSprite`, `pixiPlayerCanvas`, and per-body `_offscreenCanvas`. Previously the baked sprites were always rendered at 1× and then CSS-scaled on high-DPR devices, which meant 2×/3× DPR phones got visibly blurry bodies. Capping at 2× keeps texture memory bounded on 4× DPR outliers
- **Cracked-planet performance rewrite (v1.6.2)** — the cracked planet had been costing 50–150× as much per frame as other body types because it was emitting ~40 path strokes under an active `shadowBlur` filter every frame, which is a well-known perf hazard on Android WebView. Rewrote as a deterministic static bake via `buildCrackedSprite(b)` keyed on `b.crackSeed`, with cached gradients, and preserved the charge-up visual via an alpha ramp rather than a live `shadowBlur` ramp. The cracked planet now costs roughly the same as heart/screaming
- **Internal QA gameplay sandbox (v1.6.1)** — dev-only sandbox with scroll pauseable, manual body/powerup spawning, god mode, and live FPS observation. Not exposed to production players, used for fast iteration on apocalypse/late-phase content without having to play through 8 minutes of ramp-up each test cycle
- **Full WebGL renderer migration (v1.6.0)** — the entire render pipeline was ported from Canvas 2D to PixiJS 7 incrementally, layer by layer, behind a feature flag (`pixiActive`): star field → nebula + background imagery → 12 body types → player + trail → particle systems (pickup, death, shard, crack, destroy) → powerups + pair tethers → screen-effect overlays → unified screen shake on the stage root. Each step kept the Canvas 2D path running in parallel until the pixi path achieved visual parity, so every commit was individually shippable. The original Canvas 2D code stays in the source as a fallback for WebViews where WebGL or the PIXI CDN load fails. Net result on the test device: late-phase gameplay went from ~50–60 FPS on Canvas 2D (CPU-bound on per-frame path rebuilds) to a stable 110–120 FPS on WebGL, and the Adreno GPU mutex crash path on certain Qualcomm devices was eliminated — the Canvas 2D workload had been triggering a driver deadlock that GPU-batched sprite rendering sidesteps entirely
- **Real-time timer refactor** — every gameplay timer (powerup durations, cooldowns, combos, spawn cadences, phase thresholds) was migrated from frame-count state to wall-clock milliseconds, giving the game frame-rate-independent behaviour across 30/60/120 Hz devices and making Android low-power throttling a non-issue
- **Progressive difficulty system with phase-based content** — the game is carved into four two-minute phases that gate spawn pools, soundtrack, and background imagery, culminating in a scripted 10-minute "apocalypse" sequence. Phase selection has a reset-guard so a fresh run always starts in phase 1 regardless of prior wall-clock elapsed time
- **Complex canvas animations with dynamic hitboxes** — nine custom planet types (toothed, eye, cracked, tentacle, screaming, void, heart, mirror, skull), each procedurally drawn with pulsing/rotating/extending geometry, and several with hitboxes that follow the animation (spike tips, tentacle line-segments, pulsing-heart radius). All rendered with WebView-safe canvas operations (no `clip()`, bounded gradients, guarded degenerate paths) to avoid Android native crashes
- **Audio crossfading system** — four gameplay music tracks crossfade between phases, alongside menu/death tracks. All audio is decoded once into `AudioBuffer`s and crossfaded at loop points so transitions are inaudible
- **Orb + crystal progression** — eight unlockable orbs (five base orbs plus the Roamer / Phantasm / Helios enhanced orbs earned via the Sirius kill-threshold progression), each with a unique passive bonus and a distinct burst ability triggered by pressing both controls simultaneously; runs earn crystal currency (score × difficulty multiplier) persisted in `localStorage` to drive the shop
- **Real space imagery as parallax scenery** — NASA nebula, dying-star, galaxy, and supernova photos scroll behind the playfield using a `screen` composite blend so only the coloured light shows through
- **Play In-App Updates API integration** — the Android build uses Google Play's flexible in-app update flow so testers never have to leave the game to pick up a new build
- **Custom analytics pipeline** — a separate API Gateway → Lambda → DynamoDB path records per-run telemetry (score, time survived, death cause, phase reached, orb, powerups, burst count, streak, crystals) fire-and-forget from the game on death. Anonymous `crypto.randomUUID` session IDs persisted in `localStorage` link runs from the same install without a login; the player's pilot name is attached so the dashboard can surface per-player stats
- **Real-time analytics dashboard** — a password-protected `GET /analytics` endpoint returns a self-contained HTML page (dark theme, inline CSS) with overview stats, by-difficulty/death-cause/orb-popularity panels, phase-survival progress bars, average survival time rendered as MM:SS, and a per-pilot table with click-to-expand run history and per-difficulty breakdowns. Auto-refreshes every 60 seconds. Entirely server-rendered — no SPA, no external assets
- **Asset preloader with TAP TO START gesture gate** — boot renders a loading screen before any AudioContext work happens, fires parallel loads for all music/SFX buffers, background imagery, planet sprites, and gradient warmup, and reports per-task progress on a bar. A final TAP TO START button satisfies the browser's audio-gesture requirement, solving the "suspended AudioContext" pitfall on Android WebView and Safari without the usual first-click-anywhere hack. Includes a 15s stall timeout so one bad asset never blocks boot
- **WebView freeze mitigation on long runs** — a set of targeted fixes tracking down a ~3-minute ANR on Android: a heap-pressure watchdog sampling `performance.memory.usedJSHeapSize` every 3s and pre-emptively wiping effect arrays + gradient cache over 100 MB; bounded effect caps (nova/emp rings, trail particles, destroy/crack effects) with a per-frame `cleanupEffects()` pass; orb-trail emission throttled to every 3rd frame; the vignette gradient pre-rendered to a cached offscreen canvas per size-bucket instead of rebuilt every frame; gradient cache itself bounded and cleared at >200 entries. The game loop is wrapped in nested try/catch with a `finally { requestAnimationFrame(loop); }` so even an unexpected throw can't stall the frame chain
- **Adreno GPU driver crash diagnosis and mitigation** — identified an Android-specific crash path where WebView surface recreation during orientation / size config changes was taking out the Adreno GL driver on certain Qualcomm devices. Fix: declared `configChanges="orientation|screenSize|keyboardHidden|screenLayout|uiMode"` (plus extras) on the main activity so Android hands the event to the activity instead of recreating it; debounced the `window.resize` listener to 150 ms so a flurry of events coalesces into one atlas/gradient rebuild; added `dt` clamping (≤ 32 ms) and a `visibilitychange`-driven frame-time reset so a resumed app can never feed a stale multi-second delta into physics
- **Draw-call optimization, 538 → 229 peak (57 % reduction)** — a pass over the render pipeline to collapse per-entity canvas work. Background stars baked into four full-screen atlas canvases (160 fills → 4 `drawImage`s). Per-planet static geometry pre-rendered once at spawn into offscreen canvases for eye/skull/mirror/screaming/heart types (dozens of strokes/fills per frame → one `drawImage`). Tentacle bodies rewritten around a cached `Path2D` rather than rebuilding paths every frame. Pickup particles batched by colour × life-bucket (up to 40 particles collapse to ≤ 16 bucket fills). Destroy-effect and crack-fragment draws batched similarly
- **Resume-after-crash persistence system** — Android WebView still occasionally gets killed mid-run (backgrounding, OOM, driver reset). Gameplay state is snapshotted to `localStorage` every 5 s of play (same key overwritten, never accumulates), guarded by an age ceiling (30 min) and a minimum-survived floor (30 s) on the read side so stale or trivial runs don't clutter the menu. On next boot the main menu surfaces a gold RESUME button with the saved difficulty / elapsed / score. Clicking it runs a full-screen 3-2-1 countdown, then calls `resetGame()` and overwrites the restored fields (difficulty, orb, score, `runStartTime = now - survived*1000`, grace window) before flipping state to `'playing'`. Saved state is cleared on death, manual main-menu return, restart, and a fresh ENTER THE VOID, so resume never replays a finished run

## Tech stack

| Layer | Tech |
|-------|------|
| Game | Vanilla HTML + JS with PixiJS 7 (WebGL) primary renderer and Canvas 2D fallback — single file, no bundler, no build step |
| Mobile | Capacitor 8 wrapping the web app into a native Android shell |
| Cloud save | Google Play Games Services (`play-services-games-v2`) via a custom Capacitor Kotlin plugin (`PgsSavedGamesPlugin.kt`) — OAuth sign-in through `GamesSignInClient`, Snapshots API with `RESOLUTION_POLICY_MOST_RECENTLY_MODIFIED`, JS-side max-per-field merge |
| Backend | AWS API Gateway (HTTP API) → Lambda (Node.js 20) → DynamoDB |
| Infrastructure | Terraform with S3 remote state |
| CI/CD | GitHub Actions with OIDC federation — no long-lived AWS credentials |

## Architecture decisions

**Single HTML file game** — The entire game is one `index.html`. No bundler, no asset pipeline, no app framework. PixiJS is pulled in as a CDN `<script>` tag rather than an npm dependency so the "no build step" property is preserved. This keeps iteration fast (refresh the browser), deployment trivial (copy one file), and the mental model simple. The tradeoff is no module system, but at ~13k lines — most of it rendering and gameplay logic — it's still manageable in a single file.

**HTTP API over REST API** — API Gateway's HTTP API is cheaper (~70% less), faster (lower latency), and simpler for this use case. REST API features like request validation, WAF integration, and usage plans aren't needed for a game leaderboard.

**PAY_PER_REQUEST billing** — The leaderboard has unpredictable traffic patterns. Provisioned capacity would either waste money during quiet periods or throttle during spikes. On-demand scales to zero cost when nobody's playing.

**OIDC over long-lived keys** — GitHub Actions authenticates to AWS via OpenID Connect federation. No AWS access keys stored as secrets, no rotation needed, no risk of key leakage. The trust policy is locked to a specific repo and branch.

**Tiered DynamoDB TTL** — the leaderboard uses TTL as its retention policy instead of a cleanup job: every submission queries the current top 10 per difficulty and writes the new row with a **30-day TTL** if it lands in the top 10, or a **1-day TTL** otherwise. TTLs are decided at write time and never revisited — a row later knocked out of the top 10 keeps its original (long) TTL but is filtered out by `get-leaderboard`'s `Limit:10`, so it's invisible to players and falls off when that TTL expires. The analytics table uses a flat 90-day TTL for the same "no cleanup cron" reason.

**Custom Capacitor plugin over a community wrapper** — Google publishes no official Capacitor plugin for Play Games Services, and every community npm plugin I evaluated was built against Capacitor 4/5 and the deprecated v1 `GoogleSignInClient` (which PGS v2 removed). Rather than pin the project to a stale plugin or port one, I wrote the bridge from scratch — ~125 lines of Kotlin. Each method wraps a Google `Task<T>` into a `PluginCall` resolve/reject. `PlayGamesSdk.initialize()` runs once in `MainActivity.onCreate` before any plugin method can be invoked (avoiding a first-call race), and the plugin is registered via `registerPlugin(PgsSavedGamesPlugin.class)` before `super.onCreate` per Capacitor's contract. The upshot: the integration uses Google's current supported SDK surface with zero third-party dependency drift risk.

**Max-per-field merge instead of last-write-wins** — `RESOLUTION_POLICY_MOST_RECENTLY_MODIFIED` on `SnapshotsClient.open` handles server-side snapshot conflict auto-resolution, but that would still let one device overwrite another's higher progress if the wall clock disagreed. The JS-side merge takes `Math.max` for crystals, a set union for unlocked orbs, and top-5-per-difficulty for scores — all monotonic operations, so two devices converge on the same result regardless of write order. `activeOrb` is the only field that stays local: it's a per-device UI preference, not progression.

## What I built vs. what tools helped

The game mechanics, physics model, and visual design are my work — gravity surfing, the attract/repel two-button control scheme, procedural audio, powerup system, and all the Canvas rendering. The AWS architecture (API Gateway + Lambda + DynamoDB, OIDC auth, Terraform IaC) was designed by me based on what the project actually needs.

Claude Code was used as an implementation accelerator — turning design decisions into working code faster than typing it all out manually. The architectural choices, game design, and infrastructure decisions are mine; the tool helped me ship them.

## AWS cost estimate

**Free tier (first 12 months):**
- DynamoDB: 25GB storage, 25 read/write capacity units — the leaderboard won't come close
- Lambda: 1M requests/month free
- API Gateway: 1M HTTP API calls/month free

**Beyond free tier:**
- DynamoDB on-demand: $1.25 per million writes, $0.25 per million reads
- Lambda: $0.20 per million requests + $0.0000166667/GB-second
- API Gateway: $1.00 per million requests

At 10,000 daily active players submitting ~3 scores each: ~$1-2/month total.
